# 3D Craft 商业布局报告

**从一张图片，到用户自己游戏里的角色**  
研究日期：2026 年 9 月 9 日 · 对象：当前 Forma 3D Studio 项目

本报告将“3D Craft 赛道”理解为 AI 游戏角色及资产制作领域。基于当前代码、项目验证记录及竞品官方资料；没有取得真实收入、留存、获客成本或用户访谈数据。竞争判断属于分析，定价、预算及里程碑属于待验证方案，不是营收预测。默认小团队先面向英语独立开发者市场，保留中文，并以未来 90 天为第一阶段。

## 1. 我的判断：值得进入，但要缩小第一场战役

建议定位为：**面向独立游戏开发者和 AI 编程创作者的角色制作与交付工具，帮助他们把一个想法变成可以在自己项目中使用的角色。**

你的第一批付费用户，应该是“正在做一款游戏、缺少美术能力、需要反复制作资产”的人。手机拍照爱好者适合成为增长入口，但不能在尚未验证复购前，作为全部收入的基础。

产品的商业承诺可以是：**“Create your character. Play it. Bring it into your game.”** 现阶段宣传时，应明确自动骨骼、目标引擎适配等能力的实际支持范围。

我的优先级是：先提高可用资产的交付成功率，再接入开发者的工作流，随后验证手机端付费。保留现有视觉设计，把五款游戏作为角色测试场和分享素材。未来 90 天的主要投入应放在角色质量、绑定、优化和导入，不继续用大量新游戏扩充目录。

## 2. 我们已经具备什么，距离商业上线还缺什么

| 当前能力 | 商业价值 | 真实边界 |
| --- | --- | --- |
| 文字/图片 → 概念 → 3D，多种生成引擎 | 帮助没有建模基础的人完成第一件作品 | 质量依赖上游；还没有可证明的综合质量领先 |
| 3D 查看器、导出、模型信息 | 用户能够检查成果 | 正面好看不代表背面、拓扑和动画都可用 |
| 五个游戏，支持用户主动选择并替换为自己的模型 | 降低理解门槛，让作品立即产生情感反馈 | 使用既有物理和移动方式；并未自动完成任意模型的骨骼绑定 |
| 本地 CLI / stdio MCP | 为开发者工作流建立接口基础 | 尚非公开托管 MCP；没有完成各目标客户端的端到端商业认证 |
| Firebase 登录及前端资产同步 | 提供账户和跨端资产库的基础 | Python API 的身份校验、资产归属隔离和计费闭环仍需补齐 |
| 移动网页拍照入口、英文/中文 | 可以低成本验证手机使用场景 | 尚未发布 iOS/Android 原生应用，真机拍摄与后台恢复仍需验证 |

代码中的 credits 仍是前端状态，不能当作真实账本；直接生成任务仍有进程内状态。当前适合受控测试，不应直接按成熟多租户 SaaS 对外收费运营。依据：[商业基础](../COMMERCIAL_FOUNDATION.md)、[CLI/MCP 现状](../AGENT_ACCESS.md)、[模型进入游戏](../PLAY_YOUR_ASSET.md)，以及本轮检查的 `server/app.py`、`server/jobs.py` 和 `StudioContext.tsx`。

## 3. 优势、劣势与真正可以积累的壁垒

| 维度 | 对你的判断 | 应采取的动作 |
| --- | --- | --- |
| 优势：完整、直观的体验 | 从创作到试玩已经连起来，适合演示与第一次激活 | 展示用户自己的角色，不只展示精选样例；记录试玩是否提高导出和付费 |
| 优势：设计与迭代速度 | 界面已有辨识度，小团队能围绕细分需求快速调整 | 保持设计，减少选项干扰，让“做成一个可用角色”更明确 |
| 优势：多引擎选择 | 可以按角色、车辆、道具的效果和成本分流 | 建立同一输入的质量/成本评测；目前这是潜力，不是已验证优势 |
| 劣势：上游既是供应商也是竞争者 | 用户可能直接向同一家模型供应商购买 | 收费建立在处理、验收、版本管理和交付结果上 |
| 劣势：角色生产链有缺口 | 嘴歪、融合、穿模、动画变形会直接破坏信任 | 优先修局部、提供有限支持的绑定流程、拒绝把不可用模型标成就绪 |
| 劣势：商业基础尚未完成 | 账户、计费或任务恢复错误会导致损失 | 收费测试前补齐隔离、账本、幂等和任务恢复 |
| 机会：AI 编程带来的美术缺口 | 写游戏代码的人可能仍缺风格一致的角色 | 用真实项目验证他们是否为节省修复时间付费 |
| 威胁：功能被复制、价格下降 | 查看器、MCP 和试玩按钮都容易成为行业标配 | 积累目标引擎适配和失败修复能力，持续证明节省了多少时间 |

值得建立的长期资产有三项：

1. **可复用的角色规范。** 对支持的体型建立姿态、骨骼、材质、碰撞、动画与导出规范。第一版先限定可爱风格的双足角色；四足、翅膀和复杂机械分阶段支持。
2. **在目标游戏里验证过的交付包。** 不仅提供 GLB，还附比例、轴向、LOD、贴图预算、碰撞建议、动画和版本清单。只有实际通过相应引擎测试，才标注兼容。
3. **带授权的质量反馈。** 记录哪些错误导致用户重做、哪些修复提高采用率。先积累工作流与性能数据；私人模型默认不用于训练。供应商输出能否训练其他模型，要单独检查授权。

这些能力也能被竞争者做出来，但持续积累后，比增加游戏数量更有机会形成优势。

## 4. 竞争对手：谁最值得关注

以下是官方公开能力快照，未做统一质量实测，也不据此排名模型画质。不同厂商的 credits、网页订阅与 API 费用不能直接等同。

| 对手 | 已核实的产品能力及价格信号 | 对我们的影响 |
| --- | --- | --- |
| **Meshy** | 提供生成、处理、自动绑定和动画 API；第一方 MCP 面向 ChatGPT、Claude、Codex 等客户端。Meshy-7 带纹理图生模型 30 API credits，绑定 5，动画 3；MCP 与对应 REST 操作同价。 | 最直接的全流程竞争者。仅提供模型生成或 MCP，很难给用户换平台的理由。来源：[MCP](https://www.meshy.ai/mcp)、[API 价格](https://docs.meshy.ai/en/api/pricing)。 |
| **Tripo** | CLI 已包含 MCP、自动下载、批处理及 `game-mobile`/`game-pc` 工作流；可串联纹理、绑定和格式转换。API $1=100 credits，H2/H3 带纹理图生模型基础 30 credits，绑定 25，动画重定向每条 10，附加选项另计。 | “从 AI 编程助手生成并进入 workspace”已存在。我们要在验收和交付可靠性上竞争。来源：[CLI](https://developers.tripo3d.ai/en/docs/cli)、[API 价格](https://docs.tripo3d.ai/get-started/pricing.html)。 |
| **Hyper3D / Rodin** | 多视图、低面数、法线及纹理控制，官网列出 Unity/Unreal/Godot/Blender 插件。Creator 月付 $30、年付折算 $24/月；Business 月付 $120、年付折算 $96/月。 | 是供应商，也是直接竞争者；网页套餐不等于可转售的 API 配额。来源：[官方价格与功能](https://hyper3d.ai/pricing?lang=en)。 |
| **Sloyd** | 参数模板、图/文生成、绑定动画和引擎插件。Plus 月付 $15，Pro $50；高级操作有单独额度，“无限”受公平使用等限制。API 单独收费，带纹理图生模型基础约 $0.27。 | 既有低价压力，也有可控模板的竞争。不能假设竞争者只能生成静态模型。来源：[订阅](https://www.sloyd.ai/pricing)、[API](https://www.sloyd.ai/api/pricing)。 |
| **Polycam** | AI Capture 已支持 iOS 上拍照或上传图片生成 3D；官方该功能表暂未列 Android/Web 支持。Basic 月付 $30，年付 $150。 | 手机拍照生成 3D 已有成熟产品入口；我们的机会是角色化、试玩与游戏交付。来源：[AI Capture](https://learn.poly.cam/hc/en-us/articles/40225771390228-How-to-Create-a-3D-Model-with-AI-Capture)、[价格](https://poly.cam/pricing)。 |
| **Roblox / Cube** | 官方文档已提供生成可驾驶车辆等功能模型的流程；当前列出的固定 schema 包括 Car5 和 Body1，并通过行为脚本让部件运作。 | “生成后就能玩”也不是独占概念。Roblox 是分发合作机会，也是平台内替代者；跨引擎交付比只服务单个平台更稳妥。来源：[模型生成](https://create.roblox.com/docs/parts/model-generation)。 |
| **开源模型与现成资产** | TRELLIS.2 官方开放模型与代码；用户也可选择素材包或找美术制作。 | 用户买的是完成项目的效率。一个已绑定、风格一致的现成角色，可能比反复生成更划算。开源能力来源：[TRELLIS.2](https://github.com/microsoft/TRELLIS.2)。替代选择的性价比是本报告判断。 |

**结论：MCP 是重要分发渠道，但不是独有技术。试玩是好的体验入口，但商业价值需要落实到“这个角色是否进入了用户自己的项目”。**

## 5. 第一批客户与产品取舍

| 客户群 | 反复发生的需求 | 优先级与原因 |
| --- | --- | --- |
| 1–5 人独立游戏团队、AI 编程创作者 | 做主角、NPC、道具，快速验证游戏想法 | **第一优先。** 需求接近当前能力，能观察实际导入与修复过程 |
| Game Jam / 游戏课程组织者 | 在固定时间内让参与者完成作品 | **第二优先。** 可做班级额度包，适合集中测试；不要将一次活动当长期留存 |
| 小型游戏工作室 | 批量风格一致、协作、权限、稳定交付 | 有真实团队付费信号后推进，客单价潜力更高但要求也更高 |
| 手机宠物/创意爱好者 | 拍自己的猫、玩具、手绘角色，生成并分享 | 小规模并行试验。娱乐性强，但复购和获客成本未知 |
| AAA、精确扫描、工业资产客户 | 严格拓扑、相似度、尺寸及交付责任 | 暂不主动销售，当前产品无法稳定承诺 |

建议初期明确支持“风格化双足角色 + 少量车辆和道具”。宠物照片先转成可控姿态的角色概念，再做 3D；不承诺照片里的真实四足猫立即拥有自然奔跑动画。

外部引擎先深做一个。技术上从现有 Godot 经验延伸最快；商业上用首批 20 位目标用户的项目选择决定先做 Godot 还是 Unity。不要同时承诺 Unity、Unreal、Godot、Roblox 四套完整兼容。

## 6. 可以做手机 App 吗？可以，生成计算优先放在云端

用户完全可以在 iPhone 或 Android 上完成生成。推荐流程是：**拍照/选图 → 确认主体和角色风格 → 云端生成 → 通知完成 → 旋转查看/轻量试玩 → 同步到电脑项目。**

手机负责拍摄、编辑输入和展示；云端负责昂贵的模型生成、纹理和优化。这个建议与当前技术更匹配：TRELLIS.2 官方参考实现要求至少 24GB 显存的 NVIDIA GPU，不能把这一实现直接承诺为普通手机离线运行。未来小模型端侧能力可以另行评估。[官方运行要求](https://github.com/microsoft/TRELLIS.2)

手机端建议只突出五个动作：拍、选风格、查看、试玩、送到项目。桌面保留细节修复、版本对比与项目设置。两端共享同一账户和资产库。

| 方式 | 优点 | 代价 | 建议 |
| --- | --- | --- | --- |
| 移动 Web / PWA | 复用当前前端，iOS/Android 都能快速测试 | 拍摄、后台任务、通知和大模型渲染需真机验证 | **现在先做**完整手机闭环 |
| Capacitor + 当前 React 界面 | 可保留 UI，接入原生相机、分享、通知等能力 | WebView 中的 3D/Godot 性能仍需专项测试，封装不等于自动通过审核 | 付费信号出现后做第一版 App；[官方技术范围](https://capacitorjs.com/docs) |
| 独立原生或 React Native 客户端 | 可以更深地优化移动交互与渲染 | 前端复用减少，开发与维护成本提高 | 高频拍摄、AR 或性能瓶颈明确后投入 |

当前五游戏网页资源约 94 MiB（HTTP 压缩前），加上模型纹理，不适合作为手机首屏的必下载内容。手机版应按场景下载、先展示轻量模型，保留高质量原件供桌面导出。建议以选定的中档 iPhone 和 Android 真机达到稳定 30 FPS 作为初步验收目标，而非宣布所有设备都支持。

**地标照片的产品边界：** 拍金门大桥或埃菲尔铁塔，可以生成受照片启发的游戏道具；单张照片无法提供被遮挡面的真实信息。更准确的重建需要额外拍摄、标定和单独流程。不要用“精确扫描”描述生成式补全。我们此前的多视图实验也出现了人物和场景关系不一致，说明增加生成视角并不自动提高准确性。见[质量实验](../RECONSTRUCTION_QUALITY.md)。

商业上，先用同一套手机网页覆盖两个系统。若首批高频付费用户明显集中在 iPhone，再优先原生 iOS；否则不凭假设放弃 Android。手机产品应该与桌面共用品牌、账户和资产，而不是一开始运营两个独立业务。

## 7. 商业模式：订阅提供工作流，额度覆盖计算成本

推荐采用 **个人订阅 + 按使用量加购 + 团队方案**。生成成本、动画成本和人工处理成本必须分别计算。

以下为价格试验起点，非已上线套餐；最终额度需用真实账单和使用分布校准：

| 产品 | 建议测试价格（美元） | 用户为何付费 |
| --- | --- | --- |
| 免费体验 | $0 | 少量一次性草稿、查看和试玩；设置每账户及全站费用上限 |
| Creator | 月付 $19 与 $29 做分批价格测试 | 有限生成额度、私人资产、保存版本、完整导出、支持范围内的游戏交付 |
| Pro | 月付 $59 起测试 | 更多额度、批处理、动画/优化工具、CLI/MCP 项目工作流 |
| Team | 每团队月付 $149 起测试，明确席位数和共享额度 | 协作、权限、共享风格与资产、账单和任务记录 |
| API / Agent 使用 | 预付额度或基础服务费 + 用量 | 稳定接口、成本上限、可恢复任务和项目交付；不另收“每次 MCP 调用费” |
| 人工修复服务 | 独立报价 | 有明确交付范围的骨骼、细节、拓扑修复；前期可了解真实痛点，不能隐藏在人均低价订阅里 |

质量档位应消耗不同额度。基础草稿、高质量纹理、多个视图、绑定和动画的成本不同；用户点击前看到本次总价。已接受的概念或几何应能复用，只重做出问题的阶段。

技术失败应按清楚的规则返还预留额度；重复请求通过幂等避免重复收费。用户主观不满意可提供有限重试或付费局部修复，不承诺无限次“满意为止”。上游退款规则与给用户的退款承诺之间的差额，也要计入成本。

第一阶段不建议开放高质量无限生成，不依赖广告收入，也不急于做资产交易市场。交易市场需要足够买卖双方、权利核验、结算和争议处理。未来有真实交易需求后，再测试抽成，而不是先把“平台抽成”算进预测收入。

## 8. 单位经济：真正要看的是一个可用资产花多少钱

现有相关端点的公开基础价格示例：fal TRELLIS 为 $0.02/次，fal Rodin 为 $0.40/次；Rodin HighPack 页面标注为基础费用的 3 倍。它们是特定端点和参数的标价，不代表最新模型所有档位，也不包括整条工作流。[TRELLIS 价格](https://fal.ai/models/fal-ai/trellis)、[Rodin 价格](https://fal.ai/models/fal-ai/hyper3d/rodin)

不能用“$0.02 生成、卖 $1”直接推算利润。应记录：

**每个用户最终接受资产的成本 = 同一批次全部概念、几何、纹理、重试、绑定与优化费用 ÷ 最终接受资产数。**

若一次完整尝试成本为 $0.40，实际接受率只有 50%，则仅这部分的摊薄成本约 $0.80/件；存储、下载和客服尚未计算。接受率必须来自真实用户，不能以 HTTP 成功代替。

以下是敏感性分析，全部为假设。每月收入 $29、用户接受 20 个资产、其他可变成本 $2：Web 支付费暂按收入 3%估算；App 列暂按 15%估算。未计固定人工、固定云资源、税及获客，不能称作净利润。

| 每个接受资产的 AI 成本 | 月 AI 成本 | Web 月贡献 / 占收入 | App 月贡献 / 占收入 |
| --- | --- | --- | --- |
| $0.30 | $6 | $20.13 / 69.4% | $16.65 / 57.4% |
| $0.80 | $16 | $10.13 / 34.9% | $6.65 / 22.9% |
| $1.80 | $36 | -$9.87 / -34.0% | -$13.35 / -46.0% |

计算式：月贡献 = 收入 ×（1 − 渠道费率）− AI 成本 − 其他可变成本。15%只是情景，不是所有应用、地区和支付方式的统一费率。

因此，$29 套餐若希望 Web 可变贡献率约 65%，上述其他成本假设下，AI 成本预算应不超过约 $7.28。额度应围绕这一预算校准，并检验重度用户的满额消耗，不能只看平均用户。

再做一个规模情景：300 位用户每月平均贡献 $18，则月贡献 $5,400；如果固定运营成本为 $6,000，仍未达到收支平衡。相同假设下约需 334 位用户，且尚未加入获客费用。这是算术情景，不能当作获客或留存预测。

## 9. 手机付费、供应商与权利边界

这几项与商业模式直接相关，应在收费上线前确认：

- **商店支付。** Apple 对应用内数字功能有 IAP 规则，部分 storefront 的外链及其他安排存在例外；符合条件并加入 Small Business Program 可采用 15%佣金。Google Play 目前的费用也按地区、交易类型、安装时间及计划区分。不要将“统一 30%”或“外链就零手续费”写进商业模型。[Apple 审核指南](https://developer.apple.com/app-store/review/guidelines/)、[小企业计划](https://developer.apple.com/app-store/small-business-program/)、[Google 现行费用](https://support.google.com/googleplay/android-developer/answer/112622?hl=en-GB)
- **购买额度的规则。** Apple 指南要求通过 IAP 购买的 credits 不得过期。订阅权益与单独购买的额度，应在账本和展示上区分；具体方案按发行地区审查。[Apple IAP 规则](https://developer.apple.com/app-store/review/guidelines/#in-app-purchase)
- **不同模型的许可不同。** TRELLIS.2 模型与代码采用 MIT，但依赖有单独条款。Hunyuan3D-2.1 社区许可证明确排除欧盟、英国、韩国，另有商业及输出用途限制。不能把“开源”理解为所有地区都可无条件使用。自部署权重与第三方托管 API 应分别核对实际授权，不能相互替代。[TRELLIS.2 许可说明](https://github.com/microsoft/TRELLIS.2#-license)、[Hunyuan3D-2.1 许可证](https://github.com/Tencent-Hunyuan/Hunyuan3D-2.1/blob/main/LICENSE)
- **转售和输入权利。** “可以把模型用于商业游戏”不自动等于“可以裸模型转售”或“可以转售供应商服务”。例如 Sloyd 的公开套餐区分商业使用与 marketplace reselling。需要核对 SaaS 嵌入、分发、素材销售及训练用途；保留输入来源、模型版本、供应商与许可证记录。[Sloyd 权益差异](https://www.sloyd.ai/pricing)
- **独立品牌。** 当前项目和 UI 仍出现 Rodin、OmniCraft 等与上游重合的名字。商业发布前建立自己的品牌与清楚的供应商标注，并做名称可用性核查；本报告未进行商标检索，不代表这些名称可注册。

对于旅行照片、他人角色、品牌标识及人物照片，产品条款和上传流程应明确使用授权；不能承诺生成结果一律没有第三方权利问题。以上是需要专业审查的具体事项，不构成地区法律结论。

## 10. 获客与商业布局

**第一条渠道：开发者的真实项目。** 招募 20 位正在做游戏的创作者，分别观察“生成新角色”“修复已生成角色”“导入项目”三个任务。提供一个可运行的项目模板和一份明确的兼容说明，记录他们卡在哪里。

**第二条渠道：可复现的演示内容。** 展示“一张猫的照片 → 风格化角色 → 游戏试玩 → 导入用户项目”的完整过程；同时展示耗时、重试和局限。公开视频由用户主动选择，默认不公开私人资产。首批获客围绕 Game Jam、Godot/Unity 教程和 AI 编程社区测试，暂不大规模买广告。

**第三条渠道：开发工具集成。** 托管 MCP 和 CLI 共用同一个任务、计费、资产系统。开源薄客户端和示例可降低接入成本；付费价值放在云端处理与可靠交付。每增加一个客户端，都实际完成登录、生成、轮询、下载和撤销授权测试。

**供应链布局：** 先用已有 API 和少量可替换适配器验证需求；对受支持类别保留经过测试的备用供应商。只有生成量稳定、GPU 利用率与总体成本核算支持时，再考虑自托管。自托管的比较成本应包含空闲时间、工程维护和失败率。

**产品布局：** 同一个资产后台服务 Web、Mobile 和 Agent。游戏测试场服务创作主流程；可以衡量其激活价值，但不以“游戏时长越长越好”替代创作效率。

## 11. 90 天执行计划与停止条件

以下按 2 名全职工程师、每周有技术美术支持估算，只是排期假设。单人执行应进一步缩减到一个角色类别和一个目标引擎。

| 时间 | 交付与实验 | 决策门槛（建议目标，非行业基准） |
| --- | --- | --- |
| 第 1–14 天 | 20 位目标用户访谈/任务观察；补服务端身份与归属校验、任务持久化、费用记录；做 30 个固定输入的盲评 | 明确最常用引擎；取得 5 位愿意付费参加受控试用的用户；否则先改定位 |
| 第 15–30 天 | 一个引擎的导出包；受支持双足角色的绑定/优化试验；手机 Web 完整拍摄流程；补真实账本和失败处理 | 支持范围内的导入成功率目标 ≥90%；每个最终接受资产的成本可追踪 |
| 第 31–60 天 | 累计约 50 位合格试用者；分批测试 $19/$29；验证 MCP 客户端；测试“试玩”是否提升采用 | 累计至少 10 位真实付费者；小样本只看趋势，不宣布统计显著 |
| 第 61–90 天 | 目标 30 位累计付费用户、2 个团队试点；评估月贡献与复购；满足移动使用条件后启动 App 封闭测试 | 活跃创作者第 4 周回访目标 ≥25%；Web 可变贡献率目标 ≥60%；否则优先修质量/成本 |

App 的投入门槛建议为：已观察到约 20 位用户重复在手机创建，且拍摄、后台通知或分享确实成为主要阻碍。没有该信号时继续优化移动 Web，不因竞品有 App 就立即重写客户端。

首轮现金试验预算可封顶 $3,000（不含固定工资）：$1,000 用于推理、存储和服务；$800 用于目标用户试验补贴；$700 用于技术美术验收；$500 预备金。逐周释放预算。补贴用户必须单独分组，不能把他们的激活、付费意愿与自然用户混算。

停止或转向条件：连续两个批次无法降低人工修复时间；用户只玩样例、不把资产带入项目；在透明展示成本后仍无法获得付费；或满额用户持续产生负贡献。遇到这些结果，应缩小资产类型、提高交付能力或调整收费，而不是继续增加生成入口。

## 12. 每周只盯这些指标

**北极星指标：每周有多少位创作者，把至少一个自己接受的资产成功带入自己的项目。** 当前内置试玩与下载不能自动算作外部项目成功，后者需插件事件或用户确认。

| 指标 | 定义 | 用途 |
| --- | --- | --- |
| 首次价值时间 | 提交第一个参考到用户确认得到可用资产 | 比较入口、模板和处理流程 |
| 资产接受率 | 用户接受的资产数 / 完整生成尝试数 | 区分接口成功与实际满意 |
| 目标引擎导入成功率 | 成功导入的包 / 实际导入尝试 | 衡量交付可靠性 |
| 每个接受资产总成本 | 同批全部 AI 费用 / 接受资产数 | 决定套餐额度和供应商路由 |
| 修复时间 | 达到可用状态所需人工分钟数，报告中位数和 P90 | 证明用户为什么应该付费 |
| 第 4 周创作回访 | 激活用户中，第 4 周再次完成创作的比例 | 验证是否有持续需求 |
| 付费转换与续费 | 合格试用者付费比例、到期用户真实续费比例 | 防止把注册数当业务增长 |
| 单用户可变贡献 | 收入减渠道费、AI、可变存储/流量和客服成本 | 控制重度用户亏损 |

建议事件链：`generation_submitted → generation_completed → asset_accepted → play_started → export_downloaded → project_import_confirmed`。用同一资产/版本 ID 关联，避免把多次重试计作多位成功用户。只收集有明确用途并获得适当授权的数据。

**当前最值得投入的下一步：完成受控收费所需的后台基础，同时找 20 位有真实游戏项目的创作者，验证“减少修复并成功导入”是否足够让他们每月付费。** 手机 App 可以成为这个业务的优秀入口，但持续收入要靠用户反复完成作品。
